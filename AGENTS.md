- **Consult [`SPECIFICATION.md`](./SPECIFICATION.md)**: The authoritative, code-first language specification is available in [`SPECIFICATION.md`](./SPECIFICATION.md) at the root. It contains all grammar constructs, operator precedence, type syntax, memory model invariants, algebraic effects, state capabilities, and normative code test examples needed for development.
- **Consult [`STANDARD_LIBRARY.md`](./STANDARD_LIBRARY.md)**: The authoritative standard library specification defines the closed prelude, public library interfaces, concrete operation and resource contracts, and library conformance examples. Library contracts must obey the language's type, effect, permission, and termination rules.
- **Independent Documents**: `SPECIFICATION.md`, `STANDARD_LIBRARY.md`, and `DESIGN_RATIONALE.md` must not refer or link to one another. Keep navigation between them in `README.md`. Specifications state rules only; design motivations, comparisons, and reference sources belong in `DESIGN_RATIONALE.md`.
- **Specification Omits Design Rationale**: The specification directly states syntactic and semantic rules without explaining design motivations or rationales (design rationale belongs in `DESIGN_RATIONALE.md`).
- **Language and Library Contracts Only (No Compiler Implementation Design)**: Specifications and documentation must focus strictly on language rules, grammar, typing rules, abstract machine semantics, memory model invariants, algebraic effects, state capabilities, diagnostic error codes, and public standard library behavior. Do NOT design or include compiler implementation details (such as toolchain CLI commands, compiler internal architectures/engines, lowering pipelines, IR/AST data structures, code generators, linker strategies, or runtime engines).
- **Code-First Principle**: Lead with concrete normative code examples or signatures. Use concise rules and tables for conditions and outcomes; avoid long explanatory paragraphs and preserve distinctions between permissions, effects, and failure behavior.
